# SPICE v1 — System Documentation

> v1 = the currently running stability-domain measurement system. This document
> records its architecture, capabilities, usage and honest limits. Unlike the
> v2 (self-built engine) spec, this describes what **actually runs today**.

---

## 0. One-line positioning

**v1 is a "stability quick-screening" system**: given a protein and an
environment point (temperature, pH, ionic strength), it decides, from a
**short-window MD** run, whether that environment keeps the protein folded. Its
output is a temperature×pH **stability-domain map** plus per-point physical
metrics — the label source for SPICE.

It is **not** a general-purpose MD engine, and it **cannot** detect thermal
denaturation (see §6).

## 1. System layout (three layers)

```

│   ├─ domain.rs   two-stage scan, pruning, adaptive       │
│   │              repeats, TrendDetector, Clone template  │
│   ├─ metrics.rs  m1–m5 physical metrics                  │
│   ├─ engine.rs   SpiceEngine (state + topology + env)    │
│   ├─ builder.rs  sequence → solvation → minimization     │
│   └─ ffi.rs      Python API                              │
├─────────────────────────────────────────────────────────┤
│ dynamics (fork) — MD engine                              │
│   ├─ MdState (Clone), Velocity Verlet + SETTLE           │
│   ├─ neighbor lists: bin-cell (O(N)) + half-list + Newton│
│   ├─ nonbonded: rigid-water kernels (compact pairs +     │
│   │              shared min_image)                        │
│   └─ SPME long-range (via ewald crate)                   │
├─────────────────────────────────────────────────────────┤
│ ewald (fork) — k-space                                   │
```

Dependency chain: `spice_engine → dynamics (git fork) → ewald (git fork)`, both
patched to the `SPICE-Protein` forks (arm64 fix + PmeRecip Clone + fast math all
in one place). During development they can be swapped back to local `path`
deps.

## 2. Data flow

```
mmCIF → Structure
  → build_from_input (per pH: protonation Ash/Glh choice + solvation + L-BFGS)
  → PointTemplate (solute + minimized conformation + box, pristine Clone)
      → each environment point: engine = template.clone()   ← template never mutated
          → segment loop: set_state_rebuild + initialize_velocities(T)
              → per step engine.step(None)
                (early_abort_u hard abort + TrendDetector soft abort)
          → mref.compute → m1..m5
      → is_stable / adaptive-repeats majority vote
→ StabilityPoint (stable / crashed / build_failed / terminated_reason / metrics)
→ two-stage grid reassembly → temperature×pH matrix
```

**Key design: Clone-from-pristine.** Every point clones an independent engine
from the never-run template — this eliminated all the "template-reuse state
carryover" false crashes (SPME cache, cold-side box/PME, the 298 K full-row
crash, etc.).

## 3. Physical metrics (m1–m5)

| Metric | Meaning | Threshold (default) |
|---|---|---|
| m1 | potential-energy fluctuation (MAD/σ, spike-resistant) | 1e5 |
| m2 | Rg drift (relative to reference conformation) | 0.15 |
| m3 | secondary-structure loss (DSSP-lite main-chain H-bonds) | 0.55 |
| m4 | clash fraction (heavy-atom vdW overlap) | 0.05 |
| m5 | surface-charge mismatch (ideal vs actual) | 1.0 |

Decision: `stable = !crashed && all metrics below threshold`.

**Note**: metrics are computed at **segment-end checkpoints**, never every step
(v1 once paid ~90 ms/step for per-step O(N²) clash/surface/DSSP).

---

## 4. Protocol layer (v1's core asset)

- **Two-stage scan**: stage 1 screens every pH column at the reference
  temperature (`anchor_temp` = 310 K; builds a template + reference verdict) →
  columns that don't fold there are pruned; stage 2 walks temperature only in
  surviving columns (`bold_walk` coarse doubling + bisection).
- **Pruning**: `prune_crashed` (unstable at reference → skip whole column),
  `monotonic_prune` (temperature monotonicity), `adaptive_repeats`
  (clear-stable runs a single segment).
- **`early_abort_u`**: per-step energy > 1e4 kcal/mol → hard-abort the segment.
- **`TrendDetector`** (v2 harbinger): on long windows, judges the environment
  by trend direction (energy rising / Rg expanding / SS dissolving) with
  z-scores, 2-of-3 scoring; inert on short windows.
- **`terminated_reason`**: records why a segment stopped early
  (`energy_spike` / `energy_rise` / `rg_expand` / `ss_loss`).

## 5. Engine performance (honest numbers)

| Item | v1 measured |
|---|---|
| System size | ~18k atoms (2LYZ + 5923 OPC waters) |
| Step rate | **~16 steps/s (62 ms/step)**, CPU-only arm64 |
| Throughput | ~0.03 ns/s → **1 ns ≈ 9 h/point** |
| Build | ~60 s/point (solvation 15 s + minimization 45 s) |
| Main optimizations | bin-cell neighbors, rigid-water kernels, fast erfc/exp, early-exit, skin 2 |

**Measure speed with wall-clock**: the internal `computation_time` breakdown is
broken (undercounts ~20×, overlapping regions) and must not be trusted — v2 must
rewrite the timers.

## 6. Capability limits (must-know)

1. **Short windows cannot see thermal denaturation**: default `n_steps=20`
   (+10 equil = **60 fs**). Rg barely moves in 60 fs (m2 ≈ 0.003 vs threshold
   0.15) and SS doesn't dissolve (m3 ≈ 0.19 vs 0.55) — so **every T/pH comes
   back "stable"**. The v1 domain map is effectively a "60 fs survival map",
   not a folding-stability map.
2. **pH 0–3 is model extrapolation**: coarse protonation (Ash/Glh) + charge
   catastrophe (+12.3e), no acid-hydrolysis pathway. `py_domain_grid.py` flags
   it as `E` (untrustworthy).
3. **CPU cannot reach ns scale**: v1 is only fit for quick screening; the real
   "does it denature" answer belongs to v3 (implicit solvent / CG).
4. **CUDA GPU path not adapted**: the compact `water_full` pairs need the GPU
   kernels updated too (CUDA not built here).
5. **Machine-load noise**: 16 rayon workers on a loaded machine make throughput
   measurements noisy — benchmark on a quiet machine.

## 7. Usage

```bash
# Build (maturin develop --release → conda env spice)
cd md_cal && make install

# Single-point diagnostics (isolated = fresh build per point; reuse = template
# across temperatures)
python tests/diag_points.py --ph 7 --temp 310 --temp 388 --mode reuse

# Full 2D domain map (temperature×pH; saved to /tmp/stability_domain.txt)
python tests/py_domain_grid.py

# Engine throughput + profile (step_md path)
python tests/profile_engine.py
python tests/bench_speed.py

# Radial boundary scan
python tests/py_domain_radial.py
```

**Python API essentials**:
- `Engine.build(struct, ph, temp, pressure, ionic, relax_iters, tolerance)`
- `engine.step(action)` (with metrics; RL use) / `engine.step_md()` (bare
  advance; fast)
- `scan_stability(...)` / `scan_stability_ranges(...)` (new kwargs:
  `trend_detector` / `trend_window` / `trend_z_threshold`)
- `scan_radial(...)`

## 8. v1 → v2/v3

- **v2**: drop the `dynamics`/`ewald` engine layer; build a SoA + NEON-4-wide
  engine from scratch; **migrate the protocol layer, metrics and scan framework
  as-is**. v1's optimizations (bin neighbors, rigid water, fast erfc/exp) feed
  the v2 design spec.
- **v3**: the resolution engine (implicit solvent / CG + EDSAv2 importance-map
  driven) that answers "does it denature" for real.

**v1's deliverable**: a verified protocol, metric definitions, a scan framework,
and a pile of hard-won bug records. The engine itself is a transitional piece —
the protocol is the asset.
